## Spike 1 - CF-only mod in a Modrinth-target pack

**Question:** Does `pakku add prj --cf projecte` work in a `modrinth`-target pack, and does ProjectE land in `overrides/mods/` of the `.mrpack`?

**Commands:**
```
java -jar pakku.jar -y init -n spike -v 0.0.1 --mc-v 1.21.1 -l neoforge=21.1.172 -t modrinth
java -jar pakku.jar -y add prj --cf projecte
java -jar pakku.jar -y add create ; java -jar pakku.jar -y add sodium
java -jar pakku.jar -y export
```

**Observed:**
- `init` with flags runs non-interactively (needs `</dev/null`; `-y` is a global flag placed before the subcommand).
- `add prj --cf projecte` was **never reached/completed** (so nothing is known about how it behaves with target modrinth): `Accessing CurseForge requires the CurseForge API key ... Enter the CurseForge API key: CurseForge API key arg is empty`. No key is available in this environment (none in env, no `~/.pakku/credentials`) and one must not be written into commands/files. So "is ProjectE in `overrides/mods/`" was NOT tested empirically.
- Modrinth-only adds and export work: `[modrinth profile] exported to build/modrinth/spike-0.0.1.mrpack`, plus a serverpack zip.
- `pakku set -t multiplatform` then `export` (no CF projects) emitted three profiles (modrinth, serverpack, curseforge) without warnings.
- Pakku docs (`Exporting-a-Modpack.md`, multiplatform flow): a project not on the current platform is **included as an override** if redistributable, otherwise **ignored**. Per-project `redistributable` is set with `pakku cfg prj -r`. This is documentation evidence only.
- Unexpected finding (matters for Tasks 4/5): Pakku derives `side` from Modrinth metadata. Create is `client_side=optional, server_side=required`, which Pakku maps to `side: SERVER`, so the exported index had `"env": {"client":"unsupported","server":"required"}` and the client would not load Create. Fix verified: `pakku cfg prj -s BOTH create` gives `env client=required, server=required` (flag must come before the project arg; `pakku cfg prj create -s BOTH` fails with "Project '-s' not found"). It writes `projects.create.side` into `pakku.json`.
- Client-only mod (Sodium) exports as `client: required, server: unsupported`, as expected.
- Create 6.0.10 needs NeoForge >= 21.1.219 (Ponder >= 21.1.206); a 21.1.172 pack crashes the server with "Mod create requires neoforge 21.1.219 or above". Latest 21.1.x on the NeoForge maven at test time: 21.1.264.

**Decision:** The template keeps `target: "modrinth"` (it ships no CF mods). CF-only mods are a pack-level concern with two candidate paths, both UNVERIFIED and to verify with Engineer's Tea:
- (a) `target: multiplatform` plus a CF API key via `pakku credentials set --cf-api-key` (hypothesis from Pakku docs: redistributable CF-only mods are exported as overrides in the `.mrpack`; needs a key, then check `overrides/mods/ProjectE*.jar`).
- (b) A manual override jar under `.pakku/overrides/mods/` for permissively licensed mods such as ProjectE (MIT): no key needed, but updates are manual.

Regardless: review `side` of every Modrinth mod after `add` (Create needs `-s BOTH`), and pin NeoForge >= 21.1.219 (use current 21.1.x).

## Spike 4 - Modrinth create-version API (modpack)

**Question:** Exact `POST /version` shape for a modpack.

**Source:** ctx7 `/websites/modrinth_api` (docs.modrinth.com/api/operations/createversion) and `GET https://api.modrinth.com/v2/tag/loader`.

**Observed:**
- `multipart/form-data`; `Authorization: <PAT with VERSION_CREATE>`; fields: `data` (JSON) plus one part per file, named arbitrarily and listed in `file_parts`. `.mrpack` is an accepted extension.
- The loader tag list shows `neoforge` supports project type `modpack` (no special `mrpack` loader). Modpack `loaders` is the real loader, e.g. `["neoforge"]`.
- Required: `project_id`, `file_parts`. Also send `name`, `version_number`, `game_versions`, `version_type` (`release|beta|alpha`), `loaders`, `dependencies` (may be empty), `featured`, `status` (`listed`; `draft` allows no file), `primary_file`.

Payload shape:
```
curl -X POST https://api.modrinth.com/v2/version \
  -H "Authorization: $MODRINTH_TOKEN" -H "User-Agent: <owner>/<repo>/<ver>" \
  -F 'data={"project_id":"<ID>","name":"X 1.0.0","version_number":"1.0.0","changelog":"...",
            "dependencies":[],"game_versions":["1.21.1"],"version_type":"release",
            "loaders":["neoforge"],"featured":false,"status":"listed",
            "file_parts":["mrpack"],"primary_file":"mrpack"};type=application/json' \
  -F 'mrpack=@build/modrinth/X-1.0.0.mrpack;type=application/x-modrinth-modpack+zip'
```
`environment` and `file_types` are optional and unnecessary for modpacks. Use the project ID, not the slug.

**Decision:** The release step uses this payload with `loaders:["neoforge"]`, `game_versions:["1.21.1"]`. Not executed against the live API (no token/project); verify on the first real release, ideally with `"status":"draft"`.

## Spike 5 - ProbeJS output (desk check only; needs in-game confirmation)

**Question:** Where does ProbeJS for 1.21.1 write typings and what must `jsconfig.json` reference?

**Source:** `Prunoideae/ProbeJS` branch `1.21` (`ProbePaths.java`, `assets/probejs/dumps/jsconfig.jsonc`, `docs/installation-and-usage/page.md`). Modrinth has ProbeJS 8.0.3 and 8.0.2 for 1.21.1 neoforge. The kubejs.com wiki page describes old versions (`kubejs/probe`) and does not apply to v8.

**Observed:**
- Typings dir: `<gameDir>/.probe` (`ProbePaths.PROBE = GAMEDIR/.probe`) with `@package`, `@side-only/<side>`, `@special`, `source_jars`. Also writes `<gameDir>/.vscode/settings.json`, `<gameDir>/.gitignore`, `config/probe-settings.json`, `kubejs/exported/generated_code`.
- ProbeJS generates `jsconfig.json` into each script folder (`kubejs/startup_scripts`, `server_scripts`, `client_scripts`) from a template: `paths` map `@package`, `@package/*`, `@side-only/$side$`, `@special` to `../../.probe/...`; `include` has `./**/*.js`, `./**/*.d.ts`, `../../.probe/@package/**/*.d.ts`, `../../.probe/@side-only/$side$/**/*.d.ts`, `../../.probe/@special/**/*.d.ts`; `target ES2022`, `skipLibCheck true`.
- Dump runs automatically on world load or via `/probejs dump`. Open the game dir (parent of `kubejs`) in VSCode with the ProbeJS extension.
- Template implication: add `.probe/` to `.gitignore`; any committed `jsconfig.json` must use the `../../.probe` relative paths.

**Decision:** NEEDS IN-GAME CONFIRMATION at the Task 6 user checkpoint (that 8.0.x on this pack writes `.probe/` at the instance root and `kubejs/*/jsconfig.json` as above).
